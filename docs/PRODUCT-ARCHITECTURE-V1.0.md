# 企业级数据治理平台产品架构与 V1.0 建设计划

- 产品定位：企业级数据治理平台，以数据治理为核心，Agent 作为智能辅助能力。
- 适用场景：制造业多业务系统、多关系型数据库、内网部署。
- 当前技术基线：React + TypeScript + Vite；FastAPI + SQLAlchemy 2；PostgreSQL 16；Docker Compose；SQLAlchemy Inspector。
- 数据源范围：MySQL、SQL Server、Oracle、PostgreSQL。
- 报表平台：FineReport，纳入后续经营分析集成阶段，不作为 V1.0 数据治理核心依赖。

## 1. 产品原则

1. 治理流程优先于聊天体验：先形成资产、标准、质量、问题整改的可追踪闭环。
2. 元数据与业务数据分离：采集元数据默认只读系统目录，不批量抽取业务行。
3. AI 建议、人来确认：Agent 生成标准建议、规则建议和问题解释；未经授权和审批不得自动修改源数据或治理基线。
4. 内网优先与数据最小化：默认本地处理；调用外部模型前经过字段白名单、脱敏、审计和用户确认。
5. 可追溯：采集、规则运行、标准变更、任务流转、AI 建议均保留操作记录。
6. 渐进式架构：先强化现有 FastAPI/PostgreSQL 单体模块化结构；达到规模或异步任务需求后再拆分服务，不提前引入复杂微服务。

## 2. 目标逻辑架构

### 2.1 展示与应用层
- 治理驾驶舱：资产规模、标准覆盖、质量得分、问题闭环、采集健康度。
- 数据源管理：连接配置、凭据引用、连接测试、采集策略、运行记录。
- 数据资产目录：数据源/数据库/Schema/表/视图/字段、搜索、标签、负责人、业务域。
- 数据标准：标准分类、标准项、术语、编码/格式/值域规则、版本、审批状态。
- 数据质量：规则模板、规则配置、执行计划、结果明细、质量评分、问题工单。
- 分类分级：敏感字段识别建议、分类分级目录、人工确认、访问控制标签。
- 数据血缘：表级血缘先行，字段级血缘作为增强能力；来源、转换、下游影响。
- 治理任务：指派、期限、整改说明、复核、关闭、逾期升级。
- Agent 助手：资产问答、标准推荐、质量规则推荐、异常解释、治理报告草拟。

### 2.2 治理服务层
- 元数据服务：统一模型、采集适配器、差异比较、历史快照、采集调度。
- 标准服务：标准定义、版本、映射、审批、落标检查。
- 质量服务：规则注册、SQL/检查执行器、结果归档、评分与问题生成。
- 任务工作流：状态机、分派、通知接口、SLA。
- 血缘服务：SQL 解析适配、关系存储、影响查询。
- AI Gateway：模型路由、提示词模板、脱敏策略、输出校验、审计和限流。
- 权限审计：用户、角色、数据域权限、操作日志、敏感操作审计。

### 2.3 数据与基础设施层
- PostgreSQL：工作台业务库，保存数据源配置（不保存明文密码）、元数据目录、标准、质量结果、任务、审计。
- 源数据库连接器：MySQL / SQL Server / Oracle / PostgreSQL，只读账号优先。
- 任务执行：V1.0 初期采用 FastAPI 后台任务/独立 worker 容器；需要可靠重试和并发调度时引入 Celery/RQ + Redis。
- 文件/对象存储：保存导出报告、规则附件和审计证据；V1.0 可先使用受控本地卷。
- 日志监控：结构化日志、健康检查、任务运行指标、备份恢复。
- FineReport：后续通过受控数据集/视图/API 对接，不让报表平台直接访问治理库内部表结构。

## 3. 核心业务对象

- DataSource：数据源连接元信息、凭据环境变量引用、责任人、环境、状态。
- MetadataSnapshot / MetadataTable / MetadataColumn：采集批次、表和字段结构、注释、主外键、采集时间。
- BusinessDomain / DataOwner / AssetTag：业务域、责任部门/责任人、资产标签。
- Standard / StandardVersion / StandardMapping：标准项、版本、物理字段映射、落标状态。
- QualityRule / RuleExecution / QualityIssue：质量规则、执行批次、问题实例。
- Classification / SensitiveFieldFinding：分类分级定义、敏感字段识别结果及人工确认。
- GovernanceTask / TaskComment / TaskHistory：整改任务、处理意见、状态历史。
- LineageNode / LineageEdge：血缘节点与边，带来源类型、置信度和采集证据。
- AgentSession / AgentSuggestion / ModelCallAudit：会话、建议、模型调用审计；不得保存未脱敏原始敏感内容。

所有核心业务对象应具备创建人、创建时间、更新人、更新时间、状态和必要的版本信息。标准、规则和分类分级的变更应保留历史版本。

## 4. 关键流程

### 4.1 元数据采集
创建数据源 -> 密钥环境变量注入 -> 连接测试 -> 只读采集 -> 生成快照 -> 与上次快照比较 -> 更新目录 -> 记录运行结果和差异。采集失败不得覆盖最后一次成功快照。

### 4.2 标准治理
创建标准草稿 -> 业务/数据负责人评审 -> 发布版本 -> 将标准映射到物理字段 -> 执行落标检查 -> 生成差异问题 -> 整改和复核。

### 4.3 数据质量
选择资产 -> 配置规则模板（完整性、唯一性、有效性、一致性、及时性、准确性）-> 预览影响范围 -> 审批 -> 运行 -> 归档结果 -> 生成质量问题 -> 指派整改 -> 复测关闭。
V1.0 默认只执行只读检测 SQL；不允许规则执行器运行 DDL/DML。SQL 模板必须参数化、限制 schema/table 白名单、设置超时和扫描上限。

### 4.4 Agent 辅助治理
用户提出目标 -> 检索当前用户有权访问的元数据/标准/质量结果 -> 最小化上下文 -> 脱敏扫描 -> 用户确认外发（如调用外部模型）-> 模型生成建议 -> 输出结构校验 -> 展示依据和置信度 -> 人工采纳/驳回 -> 记录审计。
Agent 不得自行执行源库写操作、发布标准、关闭问题或修改质量规则。

## 5. 安全基线

- V1.0 生产试点前必须补齐登录认证、RBAC、数据源级权限和审计日志。
- 源数据库账号只读；按 schema/database 授予最小权限。
- 明文密码仅存在于受控环境变量或 Docker secrets；API 响应不得返回密码。
- 外部模型默认关闭；管理员配置启用后，按字段白名单和脱敏策略传输。
- 外发前显示数据类型、字段样本/上下文摘要和目标模型，要求用户确认。
- 模型调用日志只记录必要元信息、脱敏后的请求摘要、模型、耗时、token 和结果状态。
- 所有 AI 输出视为不可信建议；执行动作必须走现有业务权限和审批。
- 反向代理启用 TLS；限制网络访问；PostgreSQL 定期备份并演练恢复。
- 数据源连接、质量 SQL、导出和模型调用设置超时、限流及审计。

## 6. V1.0 版本边界与验收

### P0（V1.0 必须交付）
1. 四类数据库数据源管理和真实连接验证。
2. 元数据采集、快照、重复采集、差异、失败记录和目录检索。
3. 资产标签、业务域、负责人和资产详情。
4. 数据标准 CRUD、版本、字段映射和落标状态。
5. 质量规则模板、只读规则执行、结果归档、评分。
6. 质量问题到治理任务的指派、整改、复核、关闭闭环。
7. 基础用户认证、RBAC、操作审计、密钥安全配置。
8. 治理驾驶舱基础指标。

### P1（V1.0 后续迭代）
- 分类分级和敏感字段识别建议。
- 表级血缘和基础影响分析。
- Agent 对资产、标准、质量结果的只读问答及建议生成。
- 邮件/企业消息通知。

### 暂不纳入 V1.0
- 经营分析主题模型和指标中心。
- FineReport 深度集成。
- Agent 自动执行数据修复或源库写操作。
- 全量字段级血缘和跨平台复杂 SQL 血缘。
- 未经容量验证的微服务化/OpenMetadata 全量部署。

## 7. 开发计划（初步估算）

按 2-3 名开发人员、现有原型和元数据采集基础可复用估算；需在代码审查和内网环境确认后校准。

| 迭代 | 周期 | 主要交付 | 验收 |
|---|---:|---|---|
| Sprint 0 | 1 周 | 代码盘点、数据模型规范、迁移方案、CI、测试环境 | 本地/CI 可重复部署 |
| Sprint 1 | 1-2 周 | MySQL真实联调、SQL Server/Oracle/PostgreSQL 连接器验证、采集快照与差异 | 四类数据库至少各一套测试实例通过 |
| Sprint 2 | 2 周 | 资产目录增强、业务域、标签、负责人、搜索筛选 | 资产可搜索、归属可维护 |
| Sprint 3 | 2 周 | 标准库、版本、映射、落标检查 | 标准可发布并映射到字段 |
| Sprint 4 | 2 周 | 质量规则、只读执行、结果与评分 | 规则可执行、结果可追溯 |
| Sprint 5 | 1-2 周 | 问题工单、整改复核、驾驶舱、RBAC/审计加固 | 治理闭环可验收 |
| Sprint 6 | 2 周 | 分类分级、表级血缘、Agent 只读建议试点 | 人工确认、脱敏和审计有效 |

预计 V1.0 P0 约 8-10 周；P1 后续约 2-4 周，具体受真实数据库权限、网络、测试数据和人员投入影响。

## 8. 近期 GitHub 开发顺序

1. 先建立 Alembic 数据库迁移，停止依赖生产环境自动 create_all 演进表结构。
2. 建立统一 API 响应、分页、错误码、审计基础。
3. 完成 MySQL 真实采集验收；随后按 SQL Server、Oracle、PostgreSQL 顺序联调。
4. 实现资产业务域、标签、责任人。
5. 实现数据标准和物理字段映射。
6. 实现只读数据质量规则引擎和问题整改闭环。
7. 最后补齐 Agent Gateway、脱敏、模型调用审计和只读工具。

## 9. 已知技术债与风险

- 当前 FastAPI 启动时调用 Base.metadata.create_all，需迁移到 Alembic。
- 当前数据源连接凭据以环境变量名称引用，适合小规模试点；多租户/多环境需后续接入 Docker secrets 或企业密钥服务。
- 当前 CORS 为全开放，生产部署前必须收敛。
- 当前缺少认证、RBAC、审计，生产试点前必须完成。
- 当前采集逻辑为同步 HTTP 请求，规模扩大后需转异步任务队列。
- 当前表/字段元数据模型未覆盖完整的索引、约束、分区、视图定义、字段敏感等级等信息，按治理需求逐步扩展。
- 当前质量规则执行涉及动态 SQL，必须先实现严格白名单和只读限制，再允许连接真实业务数据库。
- 四类驱动安装和数据库方言能力须通过真实环境测试，不以 CI mock 代替内网验收。
